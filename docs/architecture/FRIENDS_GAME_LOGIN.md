# Игровой вход для друзей через AnimeOnCraft

Актуальный D-0063: основной локальный runtime25565/API уже подключены к native PLAY, основной мир прошёл save/restart. [Запуск и текущие ограничения](../operations/LOCAL_GAME_START.md). Ниже сохранены checkpoint предыдущих шагов.

2026-10-15. Владелец подтвердил, что часть друзей играет без купленной Minecraft Java. Для общего сервера выбирается собственная учётная запись AnimeOnCraft; обязательная Microsoft-привязка не подходит этому составу игроков. Решение D-0057 заменяет прежнее требование Microsoft/online-mode как единственного источника игровой identity. Backend и мод NeoForge уже реализованы и прошли отдельный локальный fixture; обычная PLAY/удалённый пользовательский запуск ещё не подключены (D-0060).

## Как будет выглядеть вход

1. Игрок входит в AnimeOnCraft по своему существующему логину и паролю.
2. При нажатии «Играть» backend проверяет аккаунт и игровой доступ, затем выдаёт короткоживущий одноразовый код входа, привязанный к аккаунту, игровому имени и серверу.
3. Наш клиентский компонент передаёт этот код серверному компоненту при подключении. Постоянный пароль не передаётся в игровом чате и не сохраняется в игровых конфигах/аргументах командной строки.
4. Сервер подтверждает код через backend до допуска в мир. Чужой ник сам по себе доступа не даёт; код нельзя использовать повторно. Ошибка проверки означает отказ во входе.

Одноразовый код создаётся автоматически; игрок не вводит второй пароль или команды `/register` / `/login` в Minecraft. Точный transport и изменения контрактов выбираются при реализации этапа 10. Этот документ не обещает уже готовый вход и не подменяет проверку реальной интеграции.

Для общей сборки используем AnimeOnCraft независимо от того, каким лаунчером друзья пользовались раньше. Наличие официального Minecraft-аккаунта не заменяет учётную запись AnimeOnCraft и не даёт административных прав на нашем сервере.

## Игровое имя и сохранения

Backend должен хранить однозначную связь пользователя с каноническим игровым именем. Имя должно соответствовать ограничениям Java Edition; регистрационный логин и игровой ник нельзя автоматически считать одинаковыми без проверки. Конфликты имён проверяются без учёта регистра; точное имя при запуске задаётся из backend.

В offline-режиме UUID зависит от имени и регистра. В локальной проверке whitelist-команда нормализовала тестовое имя в нижний регистр; поэтому для синтетического теста выбран `aoclocaltest`. При реализации допуска нельзя доверять произвольным name/UUID из клиента. Менять имя уже играющего человека без продуманного переноса inventory/сохранений нельзя. Реальные игроки пока в тестовом мире не зарегистрированы.

## Лаунчер и кланы — собственный игровой профиль

Checkpoint D-0061: в Windows-профиле добавлен выбор игрового ника. Логин аккаунта и ник — отдельные поля; до выбора показывается форма, после сохранения — закреплённый ник без кнопки переименования. Форма объясняет ограничения3–16 ASCII букв/цифр/underscore и связь с сохранениями. Повторный запрос/потерянный ответ сверяются с backend чтением; окончательное решение об уникальности/неизменяемости остаётся на сервере. После временного пароля сначала требуется смена пароля.

Renderer использует только typed IPC `game_profile_read`/`game_profile_create`. Native-код сам берёт текущую сессию, обновляет истёкший access token, проверяет ответ и отклоняет результат после выхода/смены аккаунта. Токены не возвращаются в WebView; в браузерном preview новый IPC недоступен. При успешном выборе обновляется состояние кланового доступа.

Клановые заявки/приём, назначения управляющих, independent OWNER grant, `/me/access`, состав клана, owner user search/detail теперь используют **game_profiles**. Отдельная регистрация без игрового профиля не даёт eligibility; причина отказа `GAME_PROFILE_REQUIRED`. Microsoft VERIFIED больше не выполняет это условие и не создаётся для собственного ника. Баны, ACTIVE state, MFA/step-up администратора, права управляющего только своего клана и независимое разрешение OWNER сохраняются. Contact email не требует подтверждения.

Для совместимости формы admin UserDetail поле `minecraft` сохраняет прежнюю форму `{nickname,minecraft_uuid}`, но его значения теперь взяты из собственного game_profile; это **не Microsoft binding proof**. Поиск находит игровой ник, даже если он отличается от логина/почты. Generated Community/Admin contracts и Rust reason allowlist обновлены; принятая заявка отображается как `ACCEPTED`, согласно действующему backend.

Эта часть не включает native game bridge/запуск процесса Minecraft. На момент D-0061 кнопка PLAY была закрыта; D-0062 ниже добавил native запуск. `game_admission_available=false` остаётся в community API, который сам по себе не подтверждает подготовку runtime. Серверный мод и его loopback acceptance из D-0060 работают отдельно.

## Реализованная основа игрового профиля

2026-10-15: backend теперь хранит собственный `game_profiles` отдельно от Microsoft binding. `GET /api/v1/auth/me/game-profile` возвращает `{profile:null}` до выбора; `POST` с `{game_name}` закрепляет имя за текущим аккаунтом. Нужна обычная действующая авторизация; временный пароль сначала требуется сменить. Не передавать user_id/UUID клиента: backend берёт владельца из сессии, UUID вычисляет сам.

Имя: 3–16 ASCII букв, цифр или `_`, без пробелов/переводов строк. Уникальность без учёта регистра обеспечивает БД. Исходное написание сохраняется и используется для Java-compatible offline UUID (MD5 `OfflinePlayer:<точное имя>`, UUID v3). Повторный выбор точно того же имени безопасен; другое имя и изменение регистра возвращают 409. Runtime не имеет UPDATE/DELETE для этой таблицы: обычная смена ника пока отсутствует, чтобы не потерять сохранения. Миграция не назначает ники существующим пользователям автоматически.

Проверено на отдельной PostgreSQL БД через настоящий HTTP: неверные имена/поля, повтор, конфликт регистра и одновременные запросы, отзыв сессии перед записью, запрет runtime-переименования/удаления, сохранение профиля после ручного сброса пароля. Команда `corepack pnpm@12.10.1 run test:auth`. OpenAPI описан в `packages/contracts/openapi/auth.yaml`.

Профиль сам по себе не выдаёт whitelist/grant, не снимает баны и не создаёт Microsoft VERIFIED. Формы выбора ника в лаунчере и NeoForge-компоненты ещё предстоит подключить.

## Реализованный одноразовый допуск backend

Следующий шаг D-0059: `POST /api/v1/game/tickets` с пустым телом `{}`, обычным launcher Bearer и `X-AOC-Client: launcher`. Backend выбирает настроенный сервер сам; клиент не задаёт чужой user_id, ник, UUID или server_id. Требуются собственный game profile, действующая LAUNCHER-сессия, смена временного пароля, отсутствие активных GAME/ACCOUNT банов, работающий сервер без maintenance и активное разрешение OWNER либо MEMBERSHIP. Здесь OWNER — тип разрешения whitelist, а не обход проверки для владельца проекта.

Ответ: `ticket`, `server_id`, точные `game_name`/`minecraft_uuid`, `expires_at`. Код — случайные 32 байта с префиксом `gt_`, действует 60 секунд, в БД хранится только SHA256. Новая выдача отзывает предыдущий незавершённый код этого аккаунта/сервера. Сам код и credential сервера не попадают в audit; поля ticket и Authorization закрыты logger redaction.

`POST /api/v1/game/admission/redeem` предназначен **только серверному компоненту**. Заголовок `Authorization: Bearer <серверный ключ>`, тело `{ticket, game_name, minecraft_uuid, connection_id}`; connection_id — случайный UUIDv4 конкретного серверного подключения. Сервер обязан взять имя/UUID из проверяемого подключения, сверить ответ с этим подключением и дождаться успешного ответа до допуска в мир. Не доверять самопровозглашённому нику или результату на стороне клиента. Обычный player token не подходит для redeem. Browser Origin/cookies не допускаются.

Backend повторно проверяет сессию/auth epoch, состояние аккаунта, пароль, имя/UUID, принадлежность серверу, maintenance, баны и текущее разрешение. Принимается только ещё действующий/неиспользованный код; пользовательская блокировка и условный UPDATE исключают двойное использование. Ответ содержит `accepted:true`, connection_id, user_id, ник/UUID и текущий клан либо null. Играющие без клана могут иметь независимое разрешение владельца. Выход из клана не отменяет отдельное разрешение OWNER. Архивный клан/завершённое членство не дают membership-допуск.

Настройки backend: `AOC_GAME_SERVER_ID` — UUID существующей записи game_servers, `AOC_GAME_SERVER_KEY` — отдельные случайные 32 байта в виде 64 строчных hex-символов. Ключ хранится только у backend и серверного компонента, отдельно от updater signing key; его нельзя включать в лаунчер, клиентский мод, репозиторий или раздаваемую сборку. Опциональные имена приведены в `.env.example`; реальные секреты при разработке не создавались/не менялись. При отсутствии/неверном формате настройки endpoint возвращает 503, по умолчанию допуск не включён. Этот простой вариант поддерживает один настроенный игровой сервер, без PKI/lease/outbox-инфраструктуры старого протокола.

Запрашивать код нужно после подготовки ресурсов и непосредственно перед подключением готового клиента: минутный срок не рассчитан на скачивание сборки или долгий первый запуск. Способ передачи launcher → наш клиентский компонент ещё предстоит реализовать; не помещать код в argv/конфиги/чат. Потерянный успешный ответ не допускает повторного redeem: запрашивается новый код и новое подключение.

Реальные PG/HTTP проверки входят в `test:auth` (`db/game-ticket-cases.ts`): повтор и гонка, замена кода, истечение срока, неверный сервер/ник/UUID, чужие поля, player token вместо server key, maintenance, отзыв/истечение разрешения, GAME/ACCOUNT бан, приостановка аккаунта, временный пароль, отзыв/истечение сессии, auth epoch, клан и независимый OWNER grant. Контракт: `packages/contracts/openapi/game.yaml`, генератор `scripts/game-contract.mjs`, экспорт GamePaths/GameComponents.

**Исторический checkpoint D-0060 (актуальный результат — D-0062 ниже):** [компонент NeoForge и настоящая client → server → backend → PG проверка](../operations/GAME_ADMISSION_RUNTIME.md) уже готовы в изолированном loopback fixture. Без мода/с неверным кодом — отказ до мира; действующий тестовый аккаунт вошёл. Вызова из обычной PLAY ещё нет; клиентский bridge пока только для локальной acceptance. На момент D-0060 clan workflow/`me/access` ещё использовали прежнее identity gating; переход завершён в D-0061. `game_admission_available=false` в существующем интерфейсе пока остаётся честным. Внешний запуск требует HTTPS, утверждённого адреса и последующей проверки. Обычный сервер25565 и Windows firewall не менялись.

## Что работает в игре сейчас

Только изолированный сервер этапа 9: `online-mode=false`, `enforce-secure-profile=false`, whitelist включён, **server-ip=127.0.0.1**. Скрипт запуска отказывается открывать его на другом интерфейсе. Это обычный локальный режим разработки, описанный в [NeoForge Getting Started](https://docs.neoforged.net/docs/1.21.1/gettingstarted/).

Он предназначен для проверки Minecraft/NeoForge/модов. Синтетический игрок локального теста не доказывает владение аккаунтом AnimeOnCraft. Внешний доступ не открывается, правила Windows не меняются. Сам по себе whitelist в offline-режиме не защищает от выбора чужого имени.

Обычный лаунчер пока не запускает игру. Backend и Java integration core всё ещё содержат прежние правила Minecraft binding; на этапе 10 их нужно согласованно заменить собственным игровым допуском, сохранив бан/права/кланы. Нельзя просто считать непривязанный ник `VERIFIED` или отключить проверки существующего API.

Текущие инструкции и доказательства запуска: [MODPACK_RUNTIME.md](../operations/MODPACK_RUNTIME.md). Старый [protocol v1](MINECRAFT_PROTOCOL.md) сохранён как техническая история, его online-only правила не являются новым требованием для друзей.

## Native запуск и bridge (D-0062)

Общая PLAY/Rust bridge уже проверены реальным Windows/WebView2 → Java → backend → NeoForge → PG входом в мир и EMI. Код выдаётся после challenge, Auth generation не позволяет заменить пользователя при logout/login, duplicate launch закрыт. Обычный runtime25565 ещё подключается; публичная игровая раздача/удалённый API не настроены. [Команды, конфигурация, доказательства и остаток](../operations/NATIVE_GAME_LAUNCH.md). Не реализовывать bridge заново.
